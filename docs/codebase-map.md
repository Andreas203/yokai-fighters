# Codebase map

Maintained by `gameplay-programmer` (and `ui-designer` for UI scenes). Agents read this instead of crawling the project, then pull only the files their ticket touches. Update it whenever a system is added or moved.

## Godot project (`game/`)

Godot 4.7 .NET, C# (`YokaiFighters.csproj`, net10.0). Boot: the main scene is `scenes/boot.tscn` (`Flow/GameFlow.cs`): title → control select → fight, see "Boot flow" below. `scenes/fight.tscn` is the fight on its own (the scene to open in the editor for fight work, and what tests, captures and the harness instance); it runs the YOK-39 demo flow (`FightScene.Flow.cs`, YOK-48). Its C# loader will adopt the schemas below (YOK-40).

### Run map (`game/scripts/Sim/Run/`, namespace `YokaiFighters.Sim`, YOK-76)
Pure C#, no Godot, no RNG, state = node ids only. The map is a graph of nodes joined by routes, read from data; `RunMap` is where Ryo is on it. Rows are data (where a node sits), used only to keep routes forward; the walk follows routes. No scene or UI here: YOK-77 (run flow, node → scene) and YOK-78 (map screen) build on this surface. Flow: `graph = FileMapSource.Default(ContentPaths.Data("map")).Load()`, `run = RunState.NewRun(pool, graph)`, the screen shows `run.Map.Reachable()`, `run.Map.Select(id)` → run the node (fight for `INodeType.Fight` types, opponent = `node.Yokai`) → `run.Map.Complete(id)` → back to the map until `run.Map.IsFinished`.

### Conventions
- **ids** are lowercase kebab-case and equal the file name: `data/moves/spirit-wave.json` has `"id": "spirit-wave"`. References (`clip`, `preset`) are ids, resolved as `data/clips/<id>.json` and `data/presets/<id>.json`.
- **Integers only** for gameplay numbers (determinism, F3): frames, units, percent. `mul_pct: 130` means ×1.3.
- **Frames** are 1-based from the move's first frame. Active frames are `startup+1 .. startup+active`. `"active": null` is the rules.md "—" (projectile carries the hit; needs `properties.projectile`, no body hitboxes).
- **Rects** are in gameplay units (1 unit = 1 px at 1920×1080) relative to the character's feet, x toward the opponent, y up.
- **Effects** (`{target, op, value, when?}`) are the single data-only change vocabulary for Lv 2 tuning, Lv 3 evolutions, EX versions and modifiers. `target` is a dotted path into frame data (`recovery`, `projectile.speed`, `properties.armour`); `op` is `add | mul_pct | set`; `when` is an on-screen/game-state condition, never a button.
- **Inputs**: each special stores `input.kata` (`{slot, motion}`) and `input.kihon` (`{slot, direction}`); allowed pairs are fixed by K1/K2 and both slots must match.
- **Levels**: `levels.1.frame_data` is the full Lv 1 data; `levels.2` is exactly one `tuning` effect plus a required `status`; `levels.3.evolution` needs a `preset`.
- **`status: "proposed"`** marks values awaiting the designer (e.g. every Lv 2 step, an open question). Allowed on any file and on Lv 2 / evolutions; the validator counts them.
- **`rules`** lists rules.md IDs; the validator rejects IDs that don't exist.
- Profiles' `when` values come from a fixed list of on-screen observations (P6); a button-press condition fails the schema.

### Validator (`tools/validate_data.py`)
```
pip install -r tools/requirements.txt        # jsonschema==4.26.0 (already in the dev container)
python3 tools/validate_data.py               # all of data/, skipping data/schema/ and any invalid/ folder
python3 tools/validate_data.py data/moves data/clips/foo.json
python3 -m unittest discover -s tools -p 'test_*.py'
```
Exit 0 = valid, 1 = errors, 2 = missing dependency. Errors print as `<file>: <field.path>: <message>`.
Beyond the schema it checks: id = file name; files in `data/<folder>/` have that folder's kind (`data/moves/` takes `special`, `normal` or `throw`); a normal's clip exists and matches its `frame_data` (F2); rule IDs exist; a special's clip exists and matches its frame data (total = frames_total, hit_start = startup+1, hit_end = last active frame; F2); hitboxes inside the active window; hurtbox/cancel ranges inside the move; Kata/Kihon slots match; starters are Ryo + common; cancel `offered_by` elder matches `source`; `boss` temperament and `tanuki` tier only for the Tanuki; clip hit_start ≤ hit_end ≤ frames_total; a run map (YOK-76) is a valid graph (no duplicate node ids, routes between known nodes going exactly one row forward and listed once, every node reachable from the first row, no dead end before the last row) and, only when it lists `R1` in `rules`, has R1's layout (rows 1-9; duel rows 1-3 and 6, merchant row 4, elder rows 5 and 8, merchant or dojo row 7, one `boss` node with yokai `tanuki` in row 9, row 1 = `apprentice`). Node types are not checked here: the game's registry rejects an unregistered one at load.

### Samples
`data/samples/` holds one valid file per kind (Spirit Wave + its clip, a sample light punch normal + its clip, Will-o'-wisp, Fox Step, Kitsune patient). ## Built by the goal agent (`tools/goal_agent/`)
Features written by the goal agent and accepted by its gates (build, tests, re-scan, code-critic, test-breaker). Each still needs the designer's review before it merges.
- **`copy-target`** (T2, T3, T4): `game/scripts/Sim/Run/CopyRule.cs`: `CopyRule.Target(RunState)` answers T2-T4 from the run alone and returns a `CopyTarget(Slot, Data, Level)` or null when no slot holds a special. It picks the highest-level special in a slot with no filter on move kind (T2), then the most recently levelled, then the lower slot (T3). `CopyTarget.Build(ex)` is the copy's move: Ryo's level capped at `CopyRule.HighestUnevolvedLevel` (2, so never the Lv 3 evolution) and never a modifier (T4). `RunState` records each level-up (`LevelUp`, and `Equip` of an owned special) and exposes `LevelledOrder(slot)`, a rank among the specials now in a slot (higher = more recent, 0 = never levelled or empty); replacing a slot resets it, and the ranks are stored compact (0..4) after every change. `RestoreLevelledOrder(a, b, c, d)` puts a saved order back, keeping only the relative order of the values. `StateHash` mixes the four ranks in only when some special in a slot has levelled, so other runs keep their old hash. It locks nothing (T1) and builds no fighter (T0).
- **`copy-lock`** (T1, YOK-82): `game/scripts/Sim/Run/RunSession.cs`. `Enter(nodeId)` of a node whose type is `NodeTypeRegistry.Boss` (`RunSession.IsCopyLockNode(NodeContext)`: the node type from map data, never a yokai or node id) sets `CopyLocked = true` and `LockedCopy = CopyRule.Target(Run)` before `NodeEntered` is raised. Once per run: a later boss-type node does not lock again, and a refused `Enter` locks nothing. `LockedCopy` is the `CopyTarget` record of that moment (slot, special data, level), so later changes to Ryo's slots do not reach it; it is null before the lock, and after it only when no slot held a special. `StateHash()` mixes the lock (marker, slot, special id, level) only once `CopyLocked`, so a run that has not entered a boss node keeps its earlier hash. Restored walks: the lock is never worked out again from the slots. `RunSession.Restore(run, pool, scenes, seed, copyLocked, lockedCopy)` puts a saved session back with its saved lock (for the later save, YOK-73) and throws `ArgumentException` when lock and walk disagree (locked before the walk entered a boss node, or not locked after it) or the copy is not a target (a special that is not the pool's own object, a slot not its own, a level above `MaxLevel`). The plain constructor refuses (`ArgumentException`) a run whose walk has already entered a boss node, so a session past the lock point always has its lock and a later boss-type node can never lock late. There is no way to set the lock on a live session: only `Enter` takes it. No Tanuki fighter (T0, YOK-94), no HUD (YOK-74). Tests: `game/tests/CopyLockTests.cs` (10, fixtures pool + a map and node-scene table written in the test).
