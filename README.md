# Yokai Fighters

A single-player **2.5D roguelite fighting game** for PC, built in **Godot 4 (.NET) with C#** as a 5-week capstone.

You play Ryo, an apprentice exorcist who binds yokai instead of destroying them, apologising to each one he seals into a talisman. Every yokai he beats lends him one of three abilities, so the yokai you choose to fight decide the fighter you become. At the end of every run waits the Tanuki, a shapeshifter that copies the move you have invested in most.

## The game at a glance

| | |
|---|---|
| **Run** | 8-row map, one node per row: 6 one-round duels (two against elders) and 2 rest stops, then the Tanuki. 25–40 minutes. |
| **Duel** | 60 fps, deterministic, one round. Ryo's 1,000 health carries across the run. |
| **Reward** | After each win, draft 1 of 3 abilities from the yokai you beat. Specials level up and evolve at Lv 3. |
| **Yokai** | Kitsune (zoner), Oni (rushdown), Kappa (grappler), each with two temperaments, one punishable habit and an elder twist. |
| **Boss** | The Tanuki copies your highest-level special at your level, but never your modifiers or evolution. |
| **Controls** | Kata (motion inputs, +10% precision bonus) or Kihon (one Special button). |
| **Between runs** | Unlocks by depth reached; your best special carries over at Lv 2. |

### Design pillars
1. Every upgrade changes how you fight.
2. Your fighter is yours.
3. Every choice costs something.
4. Easy to start, deep to master.
5. The game answers your habits.
6. Readable, fair fights.

## Getting started

You need Godot 4.7 (.NET; CI uses 4.7.2) and the .NET 10 SDK. Python 3.10+ runs the tools in `tools/`.

```
cd game
dotnet build
godot --headless --path . --import                         # once per fresh checkout
godot --path .                                             # play (or open game/project.godot and press F5)
godot --headless --path . res://tests/test_runner.tscn     # the full test suite; `-- only=<Class>` runs one class
godot --headless --path . res://tests/run_harness.tscn     # the whole-run bot harness (200 runs, seed 1)
```

From the repo root, the content and docs checks:

```
pip install -r tools/requirements.txt                     # once: jsonschema for the validator
python -I tools/validate_data.py                           # data/ against data/schema/
python -I tools/check_rules.py                             # the written rules over all content
python tools/data_merge_check.py --base origin/main        # the full data merge check (docs/process/data-merge-check.md)
python -I tools/check_docs.py                              # dead links and stray Markdown
```

## Assignment 3: Agent crew

The crew turns a character design into **game-ready fighting content**. Its outputs:
- rigged 3D fighters and stage assets generated through the Meshy MCP
- measured animation clips
- frame data and hitboxes derived from those clips
- reward modifiers and card text

Every piece passes a written-rules gate before it reaches the game. In this run it produced the assets and content for the game's first vertical slice, **Ryo vs the Kitsune in the bamboo grove at dusk**. That covers both fighters, nine tails, the stage props and backdrop, 41 measured clips (re-timed onto the GDD's frame targets), frame data and hitboxes for every move of both fighters, and two reward modifiers. All of it runs in a playable demo (see [Demo: the vertical slice](#demo-the-vertical-slice)).

A fighting game is unforgiving here. A move's frame data has to match what the animation shows, frame by frame, or the game feels wrong. So the crew is built around one rule, **clip first (F2)**: no frame data is written until the clip it describes has been generated *and measured*.

Its in-engine checks (overlay, model probes) also found bugs the files alone couldn't show, and each went back to the author agent |

### Architecture

Solid arrows are data flow (files the next agent reads). Dotted arrows are tool calls. Hexagons are designer approval gates: no Meshy credit is spent and no content merges without one.

```mermaid
flowchart TD
    D([Designer<br/>approves jobs, credits, gates, merges])
    O[["Orchestrator<br/>main Claude Code session<br/>runs /produce, carries outputs between agents"]]

    P["1 · producer<br/>IN: GDD, rules.md, Linear board, repo<br/>OUT: tickets + ordered dispatch plan"]
    AS["2 · asset-smith<br/>IN: character sheets, style rules<br/>OUT: generation specs → rigged models, stage, UI textures"]
    CM["3 · clip-matcher<br/>IN: rigged fighters, clip needs<br/>OUT: measured clips → data/clips/*.json"]
    MS["4 · movesmith<br/>IN: data/clips/*.json, rules tables<br/>OUT: frame data, hitboxes, modifiers, card text"]
    RL{"5 · rules-lawyer<br/>IN: content files + rules.md<br/>OUT: PASS / FAIL + rule ID"}

    G1{{"approve job list<br/>+ credit cap"}}
    G2{{"approve takes<br/>+ credit cap"}}
    G3{{"gate call: GO / fallback"}}
    M[("main branch<br/>game data")]

    LIN[(Linear<br/>YOK tickets)]
    MESHY[(Meshy MCP<br/>image · 3D · rig · animate)]
    REPO[(Repo files<br/>specs · GLBs · JSON)]

    D -- "request: build the vertical slice" --> O
    O --> P
    P -. "create / update tickets" .-> LIN
    P -- "dispatch plan" --> O

    O --> AS
    AS -- "spec + credit estimate" --> G1
    G1 -- approved --> AS
    AS -. "text/image→image, image→3D, rig" .-> MESHY
    AS -- "rigged GLBs, turnarounds, acceptance verdicts" --> REPO

    REPO -- "rigged fighters" --> CM
    O --> CM
    CM -- "clip spec + credit estimate" --> G2
    G2 -- approved --> CM
    CM -. "meshy_animate" .-> MESHY
    CM -- "retarget gate report" --> G3
    G3 -- GO --> CM
    CM -- "data/clips/*.json<br/>(frames, hit window, trim)" --> MS

    O --> MS
    MS -- "data/moves, data/modifiers<br/>(frame data from clip timing, F2)" --> RL
    MS -- "timing deviates from GDD<br/>→ re-time (trim/speed, free)" --> CM
    RL -- "FAIL + rule ID → revise (max 3 rounds)" --> MS
    RL -- PASS --> M
    GP["6 · gameplay-programmer<br/>IN: data/*.json + schemas + rules<br/>OUT: deterministic Godot game, loaders, AI, demo flow, tests"]
    M -- "data/moves, clips, modifiers, profiles, story" --> GP
    GP -- "playable build" --> DEMO([Playable demo])
    GP -- "in-engine check: hitbox overlay<br/>on the models → boxes off → fix" --> MS
    O --> GP
    O -. "status updates" .-> LIN
    D -. "reviews / merges" .-> M
```

**Coordination:** Claude Code subagents can't call each other. The main session is the orchestrator. It runs the `produce` procedure: start the producer, then dispatch each ticket through its workflow (generate → clip → content → gate). It passes each agent's output files and report on to the next agent. Agents run in parallel where tickets don't depend on each other, each in its own git worktree and branch, and every result lands as a pull request.

### The source: my GDD as a vault

### The gap and the outputs

My game is thin on written text. Three kinds of card the design calls for are missing or only part written. The pipeline wrote ten pieces to fill them, every one generated from the vault files the writing agent loaded. Each part below names the gap, where it shows in the repo, and the text that fills it.

#### 1. Wake-up cards

**The gap.** After a loss the GDD asks for "wake-up variants by row reached and by which yokai won" (rule S3 in [`docs/design/rules.md`](docs/design/rules.md)). The game varies the card by row only: [`lose-early.json`](data/story/lose-early.json), [`lose-mid.json`](data/story/lose-mid.json) and [`lose-late.json`](data/story/lose-late.json) in `data/story/` are each written to fit any yokai. No card is about the yokai that won, and none says whether a talisman carries over.

**The outputs.** Three cards, each for one yokai at one depth, written by `habit-writer`.

| Loss | Card | File |
|---|---|---|
| Oni, rows 2–3 | "{yokai} shoulders its iron club and heads back toward the snowy shrine gate without a word. You wake at the province's edge, and every talisman is blank." | [`wake-up-oni-early.json`](tools/content_pipeline/runs/whole-notes/output/wake-up-card/wake-up-oni-early.json) |
| Nine-Tailed Kitsune, row 5 | "{yokai} wanders off through the bamboo at dusk, unhurried, one tail trailing like a sleeve. You wake at the province's edge, and every talisman is blank." | [`wake-up-nine-tails-row-5.json`](tools/content_pipeline/runs/whole-notes/output/wake-up-card/wake-up-nine-tails-row-5.json) |
| Kappa, row 6 | "{yokai} bows politely, spilling a little water from its dish, and goes back to the lantern riverbank. ### How the pipeline works

```mermaid
flowchart LR
    A[".claude/agents/NAME.md<br/>lists its vault notes"] --> L["Loader: reads each note whole,<br/>cuts open questions"]
    V[(vault/*.md)] --> L
    L -->|the writer's notes| W["Writer: habit-writer or movesmith<br/>Sonnet"]
    L -->|the critic's notes| C2["Critic: rules-lawyer, Opus<br/>reads the draft against its notes"]
    W -->|draft and the lines it cites| C1["Code checks: length, sentences, placeholders,<br/>names, numbers, cited lines, copying"]
    W -->|draft| C2
    C1 -->|issues| R{any issues?}
    C2 -->|lore breaks, tone drift| R
    R -->|yes: rewrite with the issues| W
    R -->|no| O["runs/NAME/output/*.json<br/>and schema check"]
```

- **Loading** ([`vault.py`](tools/content_pipeline/vault.py)): reads the note list from the agent's file and loads each note complete, minus its "Open questions" section. There is no chunking, index or query.
- **Writing** ([`content.py`](tools/content_pipeline/content.py)): the prompt carries only the output contract (length, placeholders, JSON shape) and the notes. The model is told it knows nothing about the game except those notes. It runs with every tool off in an empty folder, so it cannot read the rest of the repo. With the text it returns one to four `sources`: the lines of the notes the text rests on, copied word for word.
- **Consistency check** ([`critic.py`](tools/content_pipeline/critic.py)): code checks for what needs no judgment, and a critic model that must quote a vault line for every issue. One code check confirms each cited line is in a note the writer loaded. Another stops the writer copying a run of eight or more words from a note.
- **Loop** ([`run.py`](tools/content_pipeline/run.py)): issues go back to the writer, for up to three drafts. Ids, triggers and rule lists are added by code, never by the model.

The pipeline takes each agent's note list from its definition file. It does not run the rest of that agent's instructions: the writer and the critic get a short role prompt, the output contract and the notes.

#### The change that made the difference: from search to whole notes

My first build treated the vault as a search problem. It split the notes into 83 sections, ranked them with BM25 and gave the writer the top four for **one query per piece**. For the Elder Kappa it returned the **Oni's** section. The text was accurate but read like a tooltip.

A second version gave each piece a hand-written query plan, one narrow query per thing the text needed, each limited to one note, with the tone sections always included. That fixed the output, but I was now choosing the notes by hand and running a search on top.

The final version drops the search. Each agent's file lists the notes it reads and it reads them whole. A vault of 13 notes fits in a prompt many times over, nothing the text needs can be missed by a bad query, and a new piece needs no query plan. The writer prompt's contract did not change.

#### What "required" means

[`features.json`](tools/goal_agent/features.json) is the bridge between the design and the code: 36 features, each with the rule IDs it implements and the evidence that proves it exists (a type, a test class, a count of data files). I wrote it by hand, and the agent holds it to the design: it refuses to run if a feature cites a rule that is not in `rules.md`, names a milestone the schedule does not use, points at the full-game stretch section, or if any rule is covered by no feature and not explicitly listed as untracked. Priority is not stored in that file at all.

#### `priority_score()`

Ranking a gap takes two steps.

**Step 1: can the agent write it right now?** A gap is skipped if any of these is true:
- **It is blocked:** something it needs is not built yet. The Tanuki fight, for example, needs the copy target first.
- **It is not code:** moves and card text go to Movesmith or the Habit Writer.
- **It has no build brief yet** in `features.json`.

Skipped gaps still get a score, but they are listed after every gap the agent can write, and the report names who they go to. That is why a gap the agent can write at 9 points sits above a content gap at 20.

**Step 2: score it.** Points are added up from six questions. Every answer is read from the design (section G of `rules.md`) or from the scan, so if I edit rule G1, the ranking changes with no change to the tool.

| Question | Points |
|---|---|
| Does G1 say it's never cut? | **+40** |
| How soon is it due (G5)? | **+30** if due this week or late, +20 next week, +10 the week after, 0 later |
| How many unbuilt features are waiting on it? | **+6 each**, counting at most 5 (so +30 max). This includes indirect waits: if A waits on B and B waits on this one, both count. |
| Is it on the cut list if the build falls behind (G2, G3)? | The earlier it gets cut, the bigger the penalty: Kata −20, meta-unlocks −16, modifiers −12, dojo trials −8, presets −4 |
| How big is it? | **−5** per size point (sizes 1 to 3) |
| Is it already half-built? | **+5** |

The agent writes the eligible gap with the highest total. In one line: build what can never be cut first, then whatever is due, then whatever unlocks the most other work, and leave anything that might be cut until last. The worked scores for the recorded run are in [Why the agent chose it](#why-the-agent-chose-it).

#### The adversaries

A writer that grades its own work will pass it. So after the mechanical gates (allowed paths, build, every existing test, the re-scan), two critics with the opposite incentive get the change:

- **code-critic** is told to assume the code is wrong and prove it against the rule text. A finding only counts if the line it quotes is really in the file and the rule it cites is really in `rules.md`; anything else is thrown away and logged. This stops a critic inventing problems.
- **test-breaker** does not argue. It writes up to eight probe tests whose expected values come from the rules, and the agent compiles and runs them in the game's test runner. A probe that fails is the finding. A probe that does not compile is discarded.

A blocking finding removes the attempt from the repo and goes back to the writer with the critic's reasoning. The writer may dispute a probe by naming the rule ID; disputed probes are not argued further, they are listed for me to decide. Advisory findings never block: they are the suggested changes in the final report.

Before the model critics run, plain code checks reject what is never acceptable here: Godot types, floats, clocks or unseeded randomness in simulation code, yokai or ability ids hard-coded in shipping code, tests that read `data/` instead of fixtures.

#### How it connects to Linear

The agent never touches Linear. It reads the design, scans the code and writes to the working tree, nothing else. The `producer` agent keeps the board in step with it on every `/produce` pass:

1. It runs `run.py gaps --json`.
2. Every gap with no ticket gets one, in score order. The gap's owner is the agent assigned, its unmet evidence is the acceptance criteria, and its rule IDs go on the ticket.
3. A gap's `blocked_by` list becomes Linear blocking relations between the tickets.
4. A ticket whose feature the scan now reports present is ready to close.

A ticket for a gap the agent can write may be run by the agent instead of a crew programmer: `run.py build --only <feature-id>` on the ticket's `YOK-<number>` branch, with the trace in the PR description. The PR then goes to my review like any other.

#### Do the critics work, or do they just complain?

A critic that always finds something proves nothing. So [`seeded_faults.json`](tools/goal_agent/seeded_faults.json) holds three faults I wrote by hand, each one line that breaks a rule in the accepted code. `critic-test` puts each one in, runs the gates as in a real attempt, and takes it out again. The critics see the whole files with no hint of where the fault is. Recorded run: [`runs/critic-seeded-faults/trace.md`](tools/goal_agent/runs/critic-seeded-faults/trace.md).

| Seeded fault | Rule | My agent's own tests | code-critic | test-breaker |
|---|---|---|---|---|
| Ties go to the least recently levelled special instead of the most recent | T3 | 7 fail | found it: "The tie-break is inverted", `CopyRule.cs:55` | 5 probes fail |
| The copy of a Lv 3 special keeps Ryo's evolution | T4 | 1 fails | found it: the constant "never clamps", `CopyRule.cs:35` | 1 probe fails |
| A full tie goes to the higher slot instead of the lower | T3 | 2 fail | found it: "the HIGHER slot wins", `CopyRule.cs:54` | 3 probes fail |

All three were caught three ways, and each critic finding named the seeded line itself rather than something nearby. With no fault seeded, the same critics passed the same code with nothing blocking, so they tell broken code from working code. Six model calls.

**To the generated game code: none.** `CopyRule.cs`, the `RunState.cs` changes and `CopyRuleTests.cs` merged in PR #89 exactly as the agent's third attempt wrote them, and `CopyRule.cs` and `CopyRuleTests.cs` have not been edited since. The three attempts were corrected by the agent's own critics, not by me. The two `.cs.uid` files beside the new scripts were generated by Godot's import step, not by the agent.

**Conditions for accepting the feature: two, both mine.** PR #89 had to merge first, because the HUD that puts the copy target on screen is built on `CopyRule.Target`. Once it was on screen, playing it showed me two things the rules had not asked for. I did not count the feature as accepted until both were fixed. Neither change touched the agent's code. Both were in the HUD the crew built on top of it:

In a yokai or elder fight that reads as if the Tanuki's copy were in play, and it is not. I changed the design (amendment [AM6](docs/design/gdd-amendments.md), rule T6) so the fight HUD shows the copy target only in the Tanuki's fight. The map and the rest-stop forecast still show it all run (YOK-118).
- **The copy reminder stayed up for the whole fight.** The strip that says what the Tanuki copies covered part of the screen for the entire Tanuki fight. I had it shown for the first 10 seconds (600 ticks) of each fight, then fade out (YOK-121, [`FightHud.cs`](game/scripts/Fight/FightHud.cs)).

The agent got the rule right. What it could not judge was how the rule should look in play. That took me playing it.

**To the agent's inputs, before the run:** the first version of the feature's brief allowed the writer only `CopyRule.cs` and its test file. T3's "most recently levelled" cannot be answered without the run recording level-ups, so I added `RunState.cs` to the files the feature may edit. **Suggested changes I have not taken yet.** The critics left four advisory findings that did not block acceptance. They are still open:

2. `CopyRuleTests.cs`: T2 says "throws included" and no test uses a throw special. Add one.

4. `RunState.cs`: the level-up order is hashed for every run with a level-up, even where it cannot change the result. Either narrow it or accept that recorded hashes of such runs change. No recorded replay was affected when it merged (all 380 tests passed, including the replay tests).

### Which existing agents became goal-oriented

My crew had ten agents when I built this. I went through each and asked one question: can it measure for itself whether it is finished, and is it safe for it to keep going until it is? (clip-matcher has since been split into `rig-specialist` and `animator`; the answer for both is the one clip-matcher got.)

| Agent | Goal-oriented now? | Why |
|---|---|---|
| `producer` | **Yes** | It planned by reading the ticket board, which only shows work someone already thought of. It now starts every pass with `run.py gaps --json` and tickets the gaps in score order. Its pass is done when every gap is ticketed, blocked with a reason, or waiting on me. How the gaps become tickets: [How it connects to Linear](#how-it-connects-to-linear). |
| `gameplay-programmer` | **Yes** | It already looped on build and tests. It now has a stated goal and stop condition: the gap its ticket names is reported present by the scan, not "the code is written". |
| `ui-designer` | No, but it gets the critics | Whether a screen is finished is a visual judgment against the concept art, and that is mine. A loop cannot check it. |
| `movesmith`, `habit-writer` | No | Their counts are easy to measure (33 abilities, 7 profiles) and the gap report now shows them, but every move waits on a clip I have approved. A loop would stall on me or write frame data with no clip, which rule F2 forbids. |
| `asset-smith`, `rig-specialist`, `animator`, `sound-scout` | No | Each step spends generation credits or money. An agent that pursues a goal by spending is the one I least want looping unattended. |
| `rules-lawyer` | No, deliberately | It is a gate. A gate with a goal of its own, such as "get content merged", is biased toward passing. Its job is to have no stake in the outcome. |
| `sparring-partner` | No | It reads results and recommends. If it could change the numbers to hit its own targets, it would be marking its own homework. |

Two new agents, both adversarial, both for code, which had no gate before (content has had the Rules Lawyer since assignment 3):

- [`code-critic`](.claude/agents/code-critic.md): reads a code branch against the written rules and rejects by file, line and rule ID. Read-only.
- [`test-breaker`](.claude/agents/test-breaker.md): writes probe tests that try to make a branch give a wrong answer and reports the ones that fail. It can write probes and nothing else.

The goal agent's in-loop critics take their briefs from these two role files ("What to attack"), so the tool and the crew attack the same things and I maintain one description. `/produce` now runs both on every code branch before it reaches my review queue, with three rounds before a ticket is marked blocked, the same shape as the Rules Lawyer gate for content.

### What I would change next

- The manifest is hand-written. The agent checks it against the design in both directions, but a feature I forgot to describe is still a feature it cannot see beyond "rule X is covered by nothing".
- The writer sees only the files a brief names. That kept it honest and cheap here, and it is why the brief needed `RunState.cs` added by hand.
- The critic in attempt 2 blocked on an input (`int.MaxValue` from a save file) that no code produced at the time. It was right, and the fix was small, but a critic with no cost for blocking will always find one more edge. The cap of four attempts is the only thing that bounds it today.
- The recorded run had a budget of one feature, so the loop's re-scan is shown once. A longer run would show it carrying on to `copy-lock`.

- Tickets live in **Linear**, team `Yokai-fighters` (key `YOK`), grouped under Epics A–F.

## Technical constraints

- Deterministic 60-tick loop. Animations are stepped by exact frames with `AnimationPlayer.Seek()`, and hitboxes are 2D rectangles in move data, so frame data is exactly true and whole-run bot tests are repeatable.
- Visual assets are generated (Tripo or Meshy; rigs also AccuRIG 2; clips also motion capture or bought packs, cleaned in Blender by script; concept art and screen plates may come from Astra) and unified by a toon shader; sound and music are sourced. Agents run only designer-approved jobs. The clip is generated and measured first, then frame data is written from it. No hand-keyed animation, no paired throws. See [`docs/design/gdd-amendments.md`](docs/design/gdd-amendments.md) (AM1, AM5, AM7).
- **Never cut:** the copy rule, the merchant, Kihon, the harness, the story cards.
- **Cut order if behind:** scope gate (end of week 1): Kata, then meta-unlocks. Balance gate (mid week 3): modifiers 14 → 8, then dojo trials, then colour-only presets.
